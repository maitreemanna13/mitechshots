1. What a Data Architect Does

A data architect designs how an organisation's data is collected, stored, connected, protected and used, so that many teams can build on it safely. Data engineers build pipelines; the architect decides the rules and the structure those pipelines fit into.

RoleMain questionTypical output
Data engineerHow do I move and transform this data?Pipelines, jobs, tables
Data modelerHow should this data be structured?Logical and physical models
Data architectHow does all our data fit together, safely, at scale?Platform design, standards, policies, decisions
Data governance leadWho owns the data, and which rules apply?Policies, roles, glossary

Thinking across the whole enterprise

An enterprise data architect is not tied to one product. Open table formats: the key to avoiding lock-in

Delta Lake, Apache Iceberg and Apache Hudi add transactions, schema evolution and time travel to Parquet files in your own storage. Because the format is open, several engines can read the same data: Spark, Trino, Snowflake, BigQuery, Athena, Fabric and Databricks all read Iceberg or Delta to some degree. Catalogs that speak the Iceberg REST protocol, such as Apache Polaris, Unity Catalog and Snowflake's catalog, let engines share one table definition. For an architect, this separates the choice of storage from the choice of engine. The next section explains which format to choose.

Compare the formats in the Delta Lake, Apache Iceberg and Apache Hudi cards. Interoperability features change quickly, so check current support for each engine before committing.

4. Medallion Architecture and Data Layers

The medallion architecture organises a lake or lakehouse into layers of increasing quality: bronze (raw), silver (cleaned and conformed) and gold (business-ready). Databricks popularised the name, but the idea is older and platform-neutral: warehouses have long used staging, integration and mart layers, and Snowflake, Fabric, BigQuery and AWS lakes use the same layering under other names.

It is a design pattern, not a product. Each layer has a clear contract: what it contains, who writes it, who may read it, and what quality it guarantees. That contract is what makes data traceable, replayable and trustworthy.

SOURCES  ->  LANDING  ->  BRONZE  ->  SILVER  ->  GOLD  ->  SERVING (BI, APIs, ML, AI)

         SOURCES          LANDING          BRONZE           SILVER           GOLD
         databases, SaaS, files exactly    raw history,     cleaned, typed,  business models,
         devices, events, as delivered,    append-only,     deduplicated,    KPIs, star
         files, APIs      short-lived      + load metadata  conformed keys   schemas

quality  unknown          unknown          as the source    validated        certified
users    source teams     ingestion jobs   engineers        engineers, DS    analysts, BI

Why each layer matters

Landing: decouples delivery from processing
Sources can deliver at any time, in any format, even when pipelines are down. Nothing is lost if a job fails, and files can be checked (checksums, manifests, virus scans) before anyone reads them.
Bronze: the system of record for replay
Because bronze keeps everything exactly as received, a bug in silver logic is fixed by reprocessing bronze, not by asking the source to resend months of data. It is also the audit evidence of what the source actually sent.
Silver: one version of the truth per entity
Data quality, deduplication, type casting, standardisation and joins across sources happen once here, so every consumer inherits the same rules instead of reinventing them.
Gold: speed and meaning for the business
Modelled for the question, pre-aggregated, documented and certified. BI stays fast and metrics mean the same in every report.

Tested: a medallion pipeline end to end

We dropped two JSON files into a landing folder. The second file contained a re-sent duplicate, an amount of "abc", a truncated line, and a later update to order 1. Then we built each layer with PySpark and Delta Lake:

from pyspark.sql import functions as F, Window

# BRONZE: read everything as strings, keep bad lines, add load metadata
bronze = (spark.read
    .schema("order_id STRING, customer STRING, amount STRING, "
            "status STRING, updated_at STRING, _corrupt_record STRING")
    .option("columnNameOfCorruptRecord", "_corrupt_record")
    .option("recursiveFileLookup", "true")  # landing/orders/2026-11-07/*.json
    .json("/lake/landing/orders")
    .withColumn("_source_file", F.col("_metadata.file_name"))
    .withColumn("_ingested_at", F.current_timestamp()))
bronze.write.format("delta").mode("append").save("/lake/bronze/orders")

# SILVER: type, validate, quarantine, keep the latest version per key
br = spark.read.format("delta").load("/lake/bronze/orders")
typed = (br.filter("_corrupt_record IS NULL")
    .withColumn("order_id", F.col("order_id").cast("int"))
    .withColumn("amount", F.expr("try_cast(amount AS DECIMAL(10,2))"))
    .withColumn("updated_at", F.to_timestamp("updated_at")))

bad = typed.filter("amount IS NULL OR amount < 0")
bad.write.format("delta").mode("append").save("/lake/quarantine/orders")

w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc())
silver = (typed.filter("amount IS NOT NULL AND amount >= 0")
    .withColumn("rn", F.row_number().over(w)).filter("rn = 1")
    .drop("rn", "_corrupt_record"))
silver.write.format("delta").mode("overwrite").save("/lake/silver/orders")

# GOLD: answer a business question
gold = (silver.groupBy("customer")
    .agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")))
gold.write.format("delta").mode("overwrite").save("/lake/gold/customer_revenue")
LayerRowsWhat happened
Landing2 files, 8 linesStored exactly as delivered
Bronze8Every line kept, including the duplicate and the truncated line, which sits in _corrupt_record with its source file name
Quarantine1Order 5 with amount "abc": try_cast returned NULL instead of failing the job
Silver4Duplicate of order 2 removed; order 1 shows its latest state, SHIPPED at 100.50
Gold3 customersC1: 2 orders, 145.50; C2: 1 order, 80.00; C3: 1 order, 300.00

A gotcha we hit: without recursiveFileLookup, reading /lake/landing/orders returned 0 rows with no error, because the files were in a date subfolder that was not named key=value. Spark only discovers subfolders as partitions in that form. Always check row counts after a landing read.

On Databricks: declarative pipelines with expectations

On Databricks the same flow is usually written as a Lakeflow Declarative Pipeline. Auto Loader picks up only new files, and expectations record, drop or fail on bad rows, with the results shown in the pipeline's event log:

import dlt  # also: from pyspark import pipelines as dp
from pyspark.sql import functions as F

@dlt.table(comment="Raw orders, exactly as landed")
def bronze_orders():
    return (spark.readStream.format("cloudFiles")  # Auto Loader
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", "/Volumes/prod/landing/_schemas/orders")
        .option("cloudFiles.schemaEvolutionMode", "rescue")  # unknown fields -> _rescued_data
        .load("/Volumes/prod/landing/orders/")
        .select("*", F.col("_metadata.file_path").alias("_source_file"),
                F.current_timestamp().alias("_ingested_at")))

@dlt.table(comment="Clean orders")
@dlt.expect_or_drop("valid_amount", "amount IS NOT NULL AND amount >= 0")
@dlt.expect("has_customer", "customer IS NOT NULL")  # record only
def silver_orders_clean():
    return (dlt.read_stream("bronze_orders")
        .withColumn("amount", F.expr("try_cast(amount AS DECIMAL(10,2))")))

dlt.create_streaming_table("silver_orders")
# create_auto_cdc_flow was called apply_changes before 2025
dlt.create_auto_cdc_flow(target="silver_orders", source="silver_orders_clean",
                  keys=["order_id"], sequence_by=F.col("updated_at"),
                  stored_as_scd_type=1)

@dlt.table(comment="Revenue per customer")
def gold_customer_revenue():
    return (dlt.read("silver_orders").groupBy("customer")
        .agg(F.count("*").alias("orders"), F.sum("amount").alias("revenue")))

On Snowflake: stages, Snowpipe and Dynamic Tables

-- landing: an external stage over cloud storage
CREATE STAGE landing.orders_stage URL = 's3://acme-landing/orders/'
  STORAGE_INTEGRATION = s3_int FILE_FORMAT = (TYPE = JSON);

-- bronze: Snowpipe loads each new file as it arrives
CREATE TABLE bronze.orders (raw VARIANT, _source_file STRING, _ingested_at TIMESTAMP_LTZ);
CREATE PIPE bronze.orders_pipe AUTO_INGEST = TRUE AS
  COPY INTO bronze.orders
  FROM (SELECT $1, METADATA$FILENAME, CURRENT_TIMESTAMP() FROM @landing.orders_stage);

-- silver: a Dynamic Table keeps itself up to date
CREATE DYNAMIC TABLE silver.orders TARGET_LAG = '15 minutes' WAREHOUSE = transform_wh AS
SELECT raw:order_id::INT AS order_id, raw:customer::STRING AS customer,
       TRY_TO_DECIMAL(raw:amount::STRING, 10, 2) AS amount,
       raw:updated_at::TIMESTAMP_NTZ AS updated_at
FROM bronze.orders
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1;

-- gold
CREATE DYNAMIC TABLE gold.customer_revenue TARGET_LAG = '1 hour' WAREHOUSE = transform_wh AS
SELECT customer, COUNT(*) AS orders, SUM(amount) AS revenue FROM silver.orders GROUP BY customer;

5. Edge, Ingestion and the Landing Zone

Before the medallion layers begin, data has to travel from where it is produced, the edge, into the platform. This is where most real-world failures start: missing files, duplicates, half-written files, schema surprises, firewalls, and sources that cannot take extra load.

What the edge layer is

The edge is everything outside the central platform that produces or first collects data: factory sensors and gateways, shop tills, mobile apps, branch servers, on-premise databases, partner SFTP servers and SaaS applications. In IoT architectures the edge also has its own compute, an edge gateway, which does useful work before sending anything:

  • Buffering when the network drops, so no readings are lost (store and forward)
  • Filtering and aggregating, for example sending one-minute averages instead of every 10 ms reading
  • Protocol translation from OPC UA, Modbus or MQTT to HTTPS or Kafka
  • Compression and encryption before data crosses the internet
  • Local decisions such as stopping a machine, without waiting for the cloud

How data should arrive in the landing zone

1. Agree an ingestion contract per source. Owner, format, schema, delivery frequency, file naming, expected volume, classification and retention. No contract, no onboarding.

2. Use a predictable path. landing/<source>/<dataset>/<yyyy-mm-dd>/<file>_<timestamp>.json, so files are easy to find, replay and expire.

3. Make "complete" explicit. Write to a temporary name and rename, or send a _SUCCESS marker or manifest listing files, row counts and checksums. Never process a file still being written.

4. Make it write-once. Ingestion roles may add files but not change or delete them; object lock or immutability policies where audit requires it.

5. Validate on arrival. Checksum, row count against the manifest, file format, malware scan for external files. Move failures to a rejected folder and alert the source owner.

6. Load into bronze incrementally and idempotently. Auto Loader, Snowpipe or COPY INTO track which files were already loaded, so a re-run never loads a file twice.

7. Expire the landing zone. Once a file is safely in bronze, lifecycle rules delete or archive it after days or weeks. Landing is a buffer, not a store.

Tested: what happens when a load runs twice

Jobs get re-run after failures, so loading from landing into bronze must be idempotent: a re-run must not load the same file again. We put two files of 5 rows each in a landing folder and compared a plain batch load with a streaming load that keeps a checkpoint:

# plain batch: no memory of what was loaded
spark.read.schema(schema).json("/lake/landing/orders")      .write.format("delta").mode("append").save("/lake/bronze/orders")

# incremental: the checkpoint records which files were processed
(spark.readStream.schema(schema).json("/lake/landing/orders")
     .writeStream.format("delta")
     .option("checkpointLocation", "/lake/_checkpoints/bronze_orders")
     .trigger(availableNow=True)  # process what is there, then stop
     .start("/lake/bronze/orders"))

8. Compatibility and Schema Evolution

Data outlives the code that writes it. A schema change that is harmless for the producer can break ten consumers, so an architect defines which changes are allowed, how they are checked, and how breaking changes are rolled out.

The four kinds of compatibility

BackwardConsumers using the new schema can read data written with the old oneUpgrade consumers first
ForwardConsumers using the old schema can read data written with the new oneUpgrade producers first
FullBoth directionsAny order
NoneNo guaranteeCoordinated release, everyone at once

Schema registries add transitive variants: the new schema must be compatible with all earlier versions, not only the previous one. This matters when consumers can replay old data, such as a Kafka topic kept for months.

Tested: which changes break readers

We wrote Avro records with one schema and read them with another, in both directions:

The pattern to remember: defaults make changes safe, renames are almost never free, and an alias only helps the new reader. That is why many teams default to full compatibility for shared topics: add optional fields with defaults, and never rename or retype in place.

Rolling out a breaking change: expand and contract

1. Expand. Add the new column or field alongside the old one, for example email_address next to email.

2. Dual-write. Producers fill both, so old and new consumers keep working.

3. Migrate consumers. Lineage lists every consumer; each moves to the new field, tracked to completion.

4. Deprecate. Announce a removal date in the catalog and data contract.

5. Contract. Remove the old field once nothing reads it, which lineage and query logs can prove.

Consistency across systems

A single Delta, Iceberg or Snowflake table gives ACID transactions. Across systems there is no shared transaction: a row can be in the orders database but not yet in the lakehouse. Architects design for eventual consistency and make the delay explicit, with a freshness SLA per dataset.

  • CAP: during a network partition a distributed system must choose between consistency and availability; most data platforms choose availability and catch up later
  • Transactional outbox: an application writes the business change and an event row in the same database transaction, and a relay publishes the event, so the two cannot disagree (see the Data Architecture Patterns card)
  • Reconciliation: compare counts and totals between source and target daily; it is the safety net for every pattern above

The idempotency patterns are tested in the Data Modelling and dbt cards, where MERGE reruns created no duplicates while plain append did.

11. Event-Driven Architecture

Instead of systems asking each other for data, an event-driven architecture has systems publish facts, such as OrderPlaced, to a durable log that many consumers read independently.

ConceptMeaning
Event vs commandAn event states something happened (OrderPlaced); a command asks for something (ShipOrder)
Topic and partitionEvents with the same key go to one partition, which preserves their order
Retention and compactionKeep events for a period, or keep only the latest value per key
Event sourcingStore every change as an event; current state is rebuilt by replaying them
CQRSSeparate models for writing and for reading, kept in sync by events
Exactly-once in KafkaIdempotent producers and transactions within Kafka; end to end needs an idempotent sink too

Design decisions

  • Choose the key carefully: ordering is only guaranteed within a partition, so key by the entity whose order matters, such as order_id
  • Govern schemas: every topic has a registered schema and a compatibility mode
  • Avoid personal data in topics where possible: messages are hard to delete from a retained log, so send IDs and keep details in a governed table
  • Plan replay: retention must cover the longest backfill you may need
  • Land events in the lakehouse: bronze tables keep the full history for analytics, beyond the topic's retention

Tested: hashing is not anonymisation

A common mistake is to hash emails with SHA-256 and call the data anonymous. We hashed two emails, then hashed a list of guessed emails and joined the two:

from pyspark.sql import functions as F

hashed = customers.select(F.sha2("email", 256).alias("email_hash"), "spend")

guesses = candidate_emails.select(
    "email", F.sha2("email", 256).alias("email_hash"))

hashed.join(guesses, "email_hash").select("email", "spend").show()
# Both customers were re-identified, with their spend.

Anyone with a list of likely emails can reverse a plain hash. A keyed hash, mixing in a secret held in a secret store, stopped the attack in our test: 0 matches. The same email still produced the same value, so joins kept working.

key = dbutils.secrets.get("privacy", "hash_key")  # never in code
pseudo = F.sha2(F.concat(F.lit(key), F.col("email")), 256)

Under laws such as GDPR, keyed hashes are still personal data, called pseudonymised data, because whoever holds the key can link them back. They lower risk; they do not remove legal duties. A dedicated keyed function such as HMAC is the stronger form of this idea.

Tested: deleting a person from a Delta table

Erasure requests are harder in a lakehouse than they look, because Delta keeps old versions for time travel. We deleted customer C200 and checked what remained:

StepResult
DELETE ... WHERE customer_id = 'C200'The current table has 2 rows
Read version 0 with time travelC200's email is still readable
VACUUM ... RETAIN 0 HOURSRefused by a safety check, unless it is turned off
VACUUM after the old files expireThe old data file is deleted
Read C200 from version 0 againFails: the data is gone
count() on version 0Still says 3, from the log's statistics, not the files
DESCRIBE HISTORYStill shows the DELETE and VACUUM, which is your evidence

So erasure is a process, not a single statement: delete from every table that holds the person, including bronze and any copies, then let VACUUM remove the old files after the retention period. Lineage tells you which tables to check.

DELETE FROM prod_sales.silver.customer WHERE customer_id = 'C200';
DELETE FROM prod_sales.gold.dim_customer WHERE customer_id = 'C200';
-- after the retention period (default 7 days), old files are removed
VACUUM prod_sales.silver.customer;
VACUUM prod_sales.gold.dim_customer;

The default retention exists to protect running readers and time travel; do not set it to zero in production. Check your retention settings against the deadline the law gives you. Raw files in bronze, exports and backups also need a deletion plan.

Many laws care about where personal data is stored and processed. This approach is often called zero trust: never trust a request because of where it comes from, verify every identity, and give the least access needed.

Example: implementing it on Databricks

Here is how the retailer answers the auditor's question, layer by layer.

1. Connect identity. Sync users and groups from the identity provider, such as Microsoft Entra ID or Okta, with SCIM. Create groups by role, for example analysts, crm-owners and data-engineers. Production jobs run as service principals, not as people.

2. Grant to groups, with least privilege. Each group gets only what its job needs. Because grants go to groups, moving a person between teams changes their access automatically.

GRANT USE CATALOG ON CATALOG prod_sales TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  prod_sales.gold TO `analysts`;
GRANT SELECT      ON SCHEMA  prod_sales.gold TO `analysts`;

GRANT ALL PRIVILEGES ON SCHEMA prod_sales.silver TO `data-engineers`;

SHOW GRANTS ON TABLE prod_sales.gold.dim_customer;

3. Protect sensitive columns. Analysts need customer counts by city, but not emails. A column mask hides the value for everyone outside an approved group, while the table stays the same.

CREATE FUNCTION prod_sales.security.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('crm-owners') THEN email
  ELSE concat(left(email, 1), '***@', substring_index(email, '@', -1))
END;

ALTER TABLE prod_sales.gold.dim_customer
  ALTER COLUMN email SET MASK prod_sales.security.mask_email;

The masking expression itself was tested in Spark: asha@example.com became a***@example.com, and a card number became ************1111.

4. Limit rows where needed. Regional teams should see only their region's orders. A row filter applies that automatically to every query.

CREATE FUNCTION prod_sales.security.region_filter(region STRING)
RETURNS BOOLEAN
RETURN is_account_group_member('sales-all-regions')
    OR (region = 'IN' AND is_account_group_member('sales-india'))
    OR (region = 'EU' AND is_account_group_member('sales-europe'));

ALTER TABLE prod_sales.gold.fact_sales
  SET ROW FILTER prod_sales.security.region_filter ON (region);

5. Scale it with tags and ABAC. Writing a mask for each table does not scale to hundreds of tables. Attribute-based access control applies one policy to every column carrying a tag, including tables created later. Databricks now recommends ABAC for this, and it became generally available in April 2026.

-- tag the column once
ALTER TABLE prod_sales.gold.dim_customer
  ALTER COLUMN email SET TAGS ('pii' = 'email');

-- one policy covers every email column in the schema
CREATE POLICY mask_emails
ON SCHEMA prod_sales.gold
COLUMN MASK prod_sales.security.mask_email
TO `account users`
FOR TABLES
MATCH COLUMNS has_tag_value('pii', 'email') AS email_col
ON COLUMN email_col;

ABAC needs Databricks Runtime 16.4 or above, or serverless compute, and some parts are still in Beta. Row filters and column masks have limits: for example, they cannot be applied to views, and time travel and clones are not supported on tables that use them.

6. Encrypt and isolate. Data is encrypted at rest and in transit. For stricter control, use customer-managed keys in the cloud key service, so that revoking the key makes the data unreadable. Use private connectivity so traffic does not cross the public internet.

7. Keep secrets out of code. Store passwords and keys in a secret scope, or in a cloud vault behind it, and read them at runtime.

password = dbutils.secrets.get(scope="etl", key="crm_db_password")

8. Audit and review. Every access is logged. Query the audit system table to answer the auditor directly, and review grants every quarter.

-- Who read the customer table in the last 30 days?
SELECT event_time, user_identity.email, action_name
FROM system.access.audit
WHERE event_date >= current_date() - INTERVAL 30 DAYS
  AND request_params.full_name_arg = 'prod_sales.gold.dim_customer'
ORDER BY event_time DESC;

The Databricks grants, masks, filters, policies and audit queries above follow the Databricks documentation; they need a Unity Catalog workspace and were not run here. Check audit column names in your workspace before relying on the query.

Snowflake uses masking policies and row access policies, both requiring Enterprise Edition or higher. A masking policy can also be attached to a tag, so every tagged column is masked.

  CASE

Example: lineage in Databricks

Unity Catalog captures lineage automatically for queries run on Databricks through Spark DataFrames or Databricks SQL. Here is what happens when the retailer's daily job runs:

1. The job runs as usual. Nothing in the code mentions lineage.

spark.sql("""
  CREATE OR REPLACE TABLE prod_sales.gold.rpt_daily_sales AS
  SELECT f.order_date, c.city, SUM(f.net_amount) AS revenue
  FROM prod_sales.gold.fact_order_line f
  JOIN prod_sales.gold.dim_customer c ON f.customer_sk = c.customer_sk
  GROUP BY f.order_date, c.city
""")

2. Unity Catalog records the links. From the query plan it learns that rpt_daily_sales reads fact_order_line and dim_customer, that revenue comes from net_amount, and which job or notebook ran it.

3. View it in Catalog Explorer. Open the table, choose the Lineage tab, then See Lineage Graph. Click a column to see its upstream and downstream columns, and filter for the jobs and dashboards that use the table.

4. Query it with SQL. Lineage is also in system tables, so it can drive reports and automation.

-- What reads dim_customer?
SELECT DISTINCT target_table_full_name, entity_type
FROM system.access.table_lineage
WHERE source_table_full_name = 'prod_sales.gold.dim_customer'
  AND event_date >= current_date() - INTERVAL 90 DAYS;

-- Where does the email column flow?
SELECT DISTINCT target_table_full_name, target_column_name
FROM system.access.column_lineage
WHERE source_table_full_name = 'prod_sales.silver.customer'
  AND source_column_name = 'email';

Unity Catalog covers what runs on Databricks. A real company also has source databases, APIs, Kafka, other Spark clusters and Airflow, so the architect has to join them into one picture. These seven steps build on each other.

2. Capture all three levels. Job-level lineage says which run produced the data. Dataset-level lineage links tables. Column-level lineage links fields, which is what you need to trace personal data and judge the impact of a column change.

3. Use OpenLineage where it fits. Choose the open standard for anything you control, such as Spark and Airflow, so that you are not tied to one vendor. Use native connectors where they are richer, such as Unity Catalog inside Databricks. Keep dataset names consistent: OpenLineage identifies a dataset by namespace and name, so the same table must get the same name from every tool, or the graph splits.

4. Store it centrally. Send everything to one metadata platform. Collibra is strongest for business governance and stewardship workflows; DataHub is open source with strong lineage and many connectors; Apache Atlas suits Hadoop-based estates. Purview is the natural choice in Microsoft-heavy companies.

5. Connect technical and business metadata. Link each table and column to a glossary term and an owner. Then the lineage graph can say "the Revenue KPI comes from CRM and Orders data, owned by the Sales domain", not only "table A feeds table B".

6. Build impact analysis. Walk the graph upstream to find causes and downstream to find what breaks. Run it automatically: when a pull request changes a column, list the affected tables, dashboards and owners, and notify them before merging.

7. Provide visualisation and audit. Users explore the graph in the catalog. Auditors get evidence: lineage for personal data, access logs, and the history of who changed what. Keep lineage history for as long as your audit period requires.

The hard part is rarely the tools. It is coverage, naming and ownership, so measure them: the percentage of tables with an owner, and the percentage of pipelines sending lineage.

Lineage interview questions with answers

Q1. What is the difference between data lineage and data provenance?
Lineage is the map of how data flows: which sources, jobs and transformations lead to a dataset, and where it goes next. Provenance is the origin and history of specific data: where a record came from, when, from which source version, and every change made to it, often used as evidence. Lineage says "revenue comes from orders through this job"; provenance says "this row came from file orders_0612.csv, loaded at 06:02 by run 8841, and was corrected on 14 June". Delta table history and audit logs provide provenance; lineage graphs provide lineage.

Q2. What is column-level lineage?
It links each column to the source columns and transformation that produce it. For example, rpt_daily_sales.revenue comes from SUM(fact_order_line.net_amount), which comes from orders.quantity × orders.unit_price. It is needed to trace personal data such as email through every copy, to judge the impact of changing one column, and to explain a metric. Tools build it from the query plan or by parsing SQL. It breaks down inside UDFs and path-based tables, which hide the column mapping.

Q3. How do you capture lineage across 100 Spark pipelines?
Never instrument each pipeline by hand; capture lineage at the platform level so new pipelines are covered automatically. On Databricks, Unity Catalog does this, provided every pipeline uses Unity Catalog tables by name, avoids RDDs, and runs on supported compute. Elsewhere, add the OpenLineage listener once, in the cluster defaults, an init script or a shared job template, with one namespace convention. Then enforce it: a CI check rejects path-based writes and missing table registration, and a coverage report lists pipelines that sent no lineage in the last week. Finally, test each job type: in our test, OpenLineage recorded a Delta write's inputs but not its output.

Q4. How do you capture lineage from Kafka to Delta Lake?
A Structured Streaming job reads the topic and writes a bronze Delta table. On Databricks, Unity Catalog records the Delta tables, but a Kafka topic is not a Unity Catalog object, so register it as external metadata (system type Kafka, entity type Topic) and link it to the bronze table with the External Lineage API, including column mappings. That external lineage shows in Catalog Explorer, but not in the lineage system tables. With OpenLineage, the Spark listener reports the Kafka topic as an input dataset, provided your version supports the source. Also collect topic schemas from the schema registry so the columns can be matched.

Q5. How do you identify downstream impact when a source column changes?
Use column-level lineage to walk downstream from the column, then expand to the jobs, dashboards and owners attached to each result. On Databricks, query system.access.column_lineage repeatedly, starting from the changed column, and join to table_lineage for jobs and dashboards. In dbt, dbt ls --select model+ lists downstream models. Automate it in CI so a pull request that drops or renames a column shows the impact list and notifies owners, and use data contracts so breaking changes need agreement first.

# Walk downstream from one column, level by level
frontier = {("prod_sales.silver.customer", "email")}
seen = set()
while frontier:
    pairs = " OR ".join(
        f"(source_table_full_name = '{t}' AND source_column_name = '{c}')"
        for t, c in frontier)
    rows = spark.sql(f"""
        SELECT DISTINCT target_table_full_name AS t, target_column_name AS c
        FROM system.access.column_lineage
        WHERE ({pairs}) AND target_table_full_name IS NOT NULL""").collect()
    frontier = {(r.t, r.c) for r in rows} - seen
    seen |= frontier
print(sorted(seen))   # every downstream column that carries email

Q6. What is the difference between technical lineage and business lineage?
Technical lineage is system-level detail: tables, columns, jobs and SQL, for engineers. Business lineage is a simplified view in business terms: "the Monthly Revenue KPI is calculated from paid orders in the Order system, owned by Finance", for analysts, auditors and managers. Business lineage is built by linking technical assets to glossary terms and owners, and hiding intermediate steps.

Q7. How does Unity Catalog capture lineage?
Automatically, at runtime. When a query runs on Databricks compute through Spark DataFrames or Databricks SQL, Unity Catalog records which tables and columns were read and written, and which notebook, job, pipeline or dashboard ran it. It aggregates this across all workspaces on the metastore. You see it in Catalog Explorer and query it in system.access.table_lineage and column_lineage, kept 395 days by default. Tables must be registered in Unity Catalog. RDDs, global temp views, renamed objects and path-based column lineage are not captured, and external systems are added through external metadata.

Q8. What is OpenLineage, and how does it integrate with Airflow?
OpenLineage is an open standard for lineage events. Each event describes a run of a job with its input and output datasets, plus extra details called facets, such as schemas or column lineage. Airflow 2.7 and later integrate through the apache-airflow-providers-openlineage package. A listener fires when tasks start, complete or fail, and gets lineage from the operator in this order: a custom extractor, the operator's own OpenLineage methods, hook-level lineage, then manual inlets and outlets. You configure a transport, such as HTTP to Marquez or DataHub, or the console for testing. Where the operator supports it, Airflow passes parent run details to Spark, so a task links to the Spark job it launched.

Q9. How would you integrate Collibra with Databricks?
Collibra connects to Unity Catalog through an Edge site or a Collibra Cloud site. You create a Databricks Workspace connection, add the Technical Lineage for Databricks Unity Catalog capability, and synchronise manually or on a schedule, then review the ingestion report. It brings in databases, schemas, tables and columns with their lineage, with volumes and notebooks in preview, but not workflows. Use a service principal with only USE CATALOG, USE SCHEMA and SELECT; Collibra recommends a dedicated catalog of lineage views rather than direct access to query history tables. Then link the ingested assets to Collibra's glossary terms, owners and policies, so that business users see governed data with lineage.

Q10. How would you maintain lineage across multiple cloud platforms?
Choose one central metadata platform, such as DataHub, Collibra or Purview, and one standard, OpenLineage, for custom pipelines. Harvest native lineage from each platform: Unity Catalog per metastore, which means per region, AWS Glue, and Microsoft Fabric or Purview. Use a single naming convention for datasets, because the graph only joins up when the same dataset has the same identity everywhere. Register shared data, such as Delta Sharing recipients or cross-cloud copies, as explicit links. Run the collectors on a schedule, measure coverage per platform, and keep ownership and glossary terms in the central catalog, so the business view stays the same whichever cloud the data is in.

AI raises the stakes for everything above. A model trained on personal data, or a chatbot that retrieves documents a user should not see, turns a governance gap into a visible incident.

Governance rules for AI data

  • Permission-aware retrieval: a retrieval-augmented (RAG) assistant must only return documents the asking user may read; filter by the user's permissions at query time, not when building the index
  • Redact before embedding: remove or mask personal data before documents become embeddings, since embeddings are hard to delete selectively
  • Lineage from data to model: record which data version trained each model, so you can retrain after an erasure request or a quality issue
  • Purpose and consent: data collected for orders may not be lawful to use for training without a proper basis
  • Regulation: the EU AI Act sets duties by risk level, phased in from 2025, so classify AI use cases as well as data

25. Implementing an Enterprise Data Lake

A data lake is cheap object storage plus the rules that stop it becoming a data swamp: files nobody can find, trust or delete. The storage is the easy part; the conventions are the architecture.

Storage layout

Separate by environment and zone at the bucket or container level, because that is where cloud permissions, encryption keys and lifecycle rules apply. Use a fixed path convention below that.

  crm/customers/ingest_date=2026-11-07/part-0000.parquet
  orders_db/orders/ingest_date=2026-11-07/...

Implementation steps

1. Set up the landing zone. Cloud accounts or subscriptions per environment, network isolation, encryption with managed keys, central logging. Do this before any data arrives.

2. Create zones with their own permissions. Ingestion roles can write raw; only pipelines write curated and gold; analysts read gold. Deny public access everywhere.

3. Register everything in a catalog. Glue Data Catalog, Unity Catalog, Purview or Knowledge Catalog. A file that is not in the catalog does not exist for consumers.

4. Standardise ingestion. One framework, with a metadata contract per source: owner, classification, schema, frequency, retention. Reject sources without an owner.

5. Choose formats. Keep raw in the delivered format or Parquet; use an open table format from curated onwards, so you get updates, deletes and schema evolution.

6. Apply lifecycle rules. Landing files expire in days, sandbox in weeks, raw moves to cheaper storage classes after months, archive follows legal retention.

7. Add quality and lineage. Checks between zones; lineage captured automatically where possible.

8. Publish and measure. Track the share of datasets with an owner, a description and a classification. Falling numbers are the first sign of a swamp.

2. Build the self-serve platform. A product template that creates storage, a catalog or schema, CI/CD, quality checks and access groups from the specification above.

3. Define global standards. Naming, classification tags, security policies, interoperability formats and SLO reporting, enforced by the platform rather than by review meetings.

4. Publish products to a marketplace. A catalog where consumers find products, read contracts and request access.

5. Share between domains without copying. Use the platform's sharing features, so domains consume each other's products in place.

29. Modernising Legacy Systems

Most enterprises do not start from scratch. They have a warehouse appliance, a Hadoop cluster, decades of ETL jobs and perhaps a mainframe. Modernisation moves these to a cloud platform without breaking the business while it happens, which is why it is a programme of waves, not a single project.

Why modernise

  • Hardware or licence end of life, and rising support costs
  • Fixed capacity that cannot scale for month-end or AI workloads
  • Skills scarcity for old technologies
  • No support for streaming, unstructured data or machine learning
  • Governance gaps: no lineage, coarse access control

A modernisation programme, phase by phase

1. Discover. Inventory every table, job, report and user. Usage logs and lineage show what is really used; it is common to find a large share of reports and tables nobody reads, which can be retired instead of migrated.

2. Assess and plan. Score each workload by business value and migration complexity, group them into waves by domain, and build the business case on total cost, including running both systems in parallel.

3. Build the foundation. Landing zone, network, identity, catalog, security policies, CI/CD and the ingestion framework, before the first wave.

4. Migrate a pilot wave. One domain end to end: bulk-load history, keep it current with CDC, convert and test the code, and rebuild its reports.

5. Validate by reconciliation. Prove the new platform gives the same answers as the old one, at several levels (below).

6. Run in parallel, then cut over. Both systems run side by side for an agreed period; consumers switch domain by domain once results match.

7. Decommission. Switch off legacy jobs and hardware wave by wave. Savings only appear when the old system is actually turned off.

def profile(df, key, cols):

    return df.agg(F.count("*").alias("rows"),
                  F.countDistinct(key).alias("keys"),
                  F.sum("amount").alias("sum_amount"),

    print(k, "match" if s[k] == t[k] else f"DIFF {s[k]} vs {t[k]}")
